# Задание 4 — изменения и ответы

Документ повторяет десять Demo из `EXERCISE_4 (1).md`. Для каждой Demo кратко указано, что мы
изменили, и даны ответы на вопросы.

React-версия запускается через `/?react=1`.

## Demo 1 — JSX, компоненты, props и `children`

### Что мы изменили?

- Создали `PersonCard`, `LocationCard`, `TimelineEventCard`, `PeopleSection`, `LocationsSection` и
  `TimelineFilters`.
- Все props типизированы через TypeScript, `any` не используется.
- `ContentPanel` получает именованный prop `title`, а содержимое страницы — через `children`.

### Ответы

1. **Что можно написать внутри `{...}`?**
   Например, `{person.name}`, `{people.length}` или тернарное выражение. В фигурных скобках можно
   использовать JavaScript-выражения, которые возвращают значение. Statements `if`, `for`, `switch`
   и объявления переменных нужно писать до JSX.

2. **Что TypeScript проверяет в props?**
   `PersonCard` ожидает полный объект `Person`. Временный пример `<PersonCard person="Nova" />`
   вызывает ошибку типов, потому что строка не является `Person`. Неправильный пример нельзя
   оставлять в итоговом коде.

3. **Именованный prop или `children`?**
   Именованный prop имеет конкретное назначение, например `title` или `person`. `children` — это
   гибкое содержимое между тегами компонента. Поэтому у `ContentPanel` заголовок передаётся отдельно,
   а содержимое панели — через `children`.

4. **Почему нельзя изменять DOM напрямую?**
   React предполагает, что сам управляет DOM внутри своего root. Ручные изменения через `innerHTML`,
   `classList` или `appendChild` могут рассинхронизировать настоящий DOM и React-дерево, а следующий
   render способен затереть такие изменения.

## Demo 2 — условный рендеринг

### Что мы изменили?

- Для пустых списков People и Locations показывается сообщение вместо пустого grid.
- Responsibilities выводятся только при их наличии.
- Timeline показывает сводку фильтра или предупреждение в зависимости от URL.
- `getCertaintyTone()` выбирает цвет Badge для события.

### Ответы

1. **Где используется `&&`?**
   В `PersonCard` используется `hasResponsibilities && (...)`. Значение `hasResponsibilities`
   является boolean, потому что вычисляется через `length > 0`. Если слева было бы число `0`, React
   мог бы вывести `0` на страницу.

2. **Почему `null` лучше пустого `<div>`?**
   `null` вообще не создаёт DOM-узел. Пустой `<div>` создаёт лишний элемент и может влиять на layout.
   В текущем коде `null` не используется: при отсутствии данных выводится полезное сообщение, а
   необязательные блоки пропускаются через `&&`.

## Demo 3 — вывод коллекций

### Что мы изменили?

- People выводятся с `person.id`, Locations — с `location.id`, Timeline Events — с `event.id` в
  качестве `key`.

### Ответ

React использует `key`, чтобы узнавать один и тот же соседний элемент между renders. Благодаря этому
React правильно обрабатывает добавление, удаление и перестановку и сохраняет нужный DOM и локальное
состояние компонента. `key` не передаётся компоненту как обычный prop.

## Demo 4 — стабильные keys и идентичность

### Что мы изменили?

- Создали учебный маршрут `/key-demo`.
- В Demo используются uncontrolled inputs, а `?order=reverse` переворачивает список.
- `key={index}` специально оставлен видимым, чтобы показать неправильную связь записей.
- Все настоящие списки используют стабильные ID.

### Ответы

1. **Что происходит при отсутствующих, повторяющихся или индексных keys?**
   Без key React показывает warning и в основном сопоставляет элементы по позиции. Повторяющиеся keys
   делают идентичность неоднозначной. Индекс относится к позиции, а не к записи, поэтому после
   сортировки или фильтрации DOM-state, focus или введённое значение могут перейти к другой записи.

2. **Ошибка видна пользователю?**
   Да. Если изменить текст первого input и перевернуть список, введённое значение останется на первой
   позиции, хотя там уже находится другая запись. Это не только предупреждение в Console.

3. **Когда допустим `key={index}`?**
   Только для полностью статичного списка без стабильных ID, который никогда не сортируется, не
   фильтруется, не дополняется, не сокращается и не содержит локального состояния элементов. В этом
   проекте настоящие данные уже имеют ID.

> **Открытый пункт:** перед окончательной сдачей после демонстрации нужно заменить в
> `KeyIdentityDemo` значение `key={index}` на `key={item.id}`. Сейчас правильный вариант находится
> только в комментарии.

## Demo 5 — presentational- и feature-компоненты

### Что мы изменили?

Разделили крупные части на маленькие компоненты. В частности, Timeline теперь состоит из
`TimelinePage`, `TimelineFilters` и `TimelineEventCard`.

### Классификация

- **Feature/container:** `App`, `AppRoutes`, `Navigation`, `DashboardPage`, `PeopleLocationsLayout`,
  `PersonDetailsPage`, `TimelinePage`, `KeyIdentityDemo`.
- **Presentational:** `Header`, `Footer`, `PlaceholderPage`, `NotFoundPage`, небольшие компоненты
  Dashboard, `PeopleSection`, `LocationsSection`, `PersonCard`, `LocationCard`, `ContentPanel`,
  `TimelineFilters`, `TimelineEventCard`, `Badge`.

### Ответы

1. **За что отвечают разделённые части?**
   `TimelinePage` читает query-параметр и подготавливает видимые данные. `TimelineFilters` выводит
   фильтры, а `TimelineEventCard` — одно событие. Разметку карточки можно изменить без изменения
   фильтрации, пока контракт props остаётся прежним.

2. **Как мы проводили границу?**
   Feature/container знает о URL, выборе и подготовке данных. Presentational-компонент получает
   готовые props и в основном отвечает только за отображение.

## Demo 6 — структура по features

### Что мы изменили?

```text
src/react/
├── app/
├── features/
│   ├── dashboard/
│   ├── key-identity/
│   ├── people-locations/
│   └── timeline/
└── shared/components/
```

### Ответы

1. **Структура по типам или по features?**
   При структуре по типам все компоненты, hooks или pages лежат в отдельных общих папках. Структура
   по features хранит рядом всё, что относится к одному разделу. Для проекта это понятнее, потому что
   Dashboard, People & Locations и Timeline являются отдельными областями.

2. **Когда компонент становится `shared`?**
   Компонент остаётся локальным, если нужен только одному feature, например `PersonCard` или
   `ContentPanel`. Он переносится в `shared`, когда реально используется разными features. `Badge`
   используется в Dashboard и Timeline.

## Demo 7 — повторно используемые UI-компоненты

### Что мы изменили?

Создали типизированный компонент `Badge`. Он используется в `CaseSummary`, `RecentEvidence` и
`TimelineEventCard`.

### Ответы

1. **Что меняется через props, а что остаётся внутри компонента?**
   `tone` и `children` меняют цвет и текст. Тег `<span>`, основной класс `badge` и соответствие
   `tone` CSS-классу остаются внутри компонента.

2. **В чём преимущество перед копированием HTML-строк?**
   `Badge` даёт одну реализацию и типизированный API. Стиль или разметку нужно менять только в одном
   месте. Скопированные HTML-шаблоны легко начинают отличаться друг от друга.

## Demo 8 — маршрутизация

### Что мы изменили?

- Подключили React Router и `HashRouter`.
- Dashboard, People, Locations и Timeline получили настоящие маршруты.
- People и Locations реализованы как вложенные маршруты через `NavLink` и `Outlet`.
- Маршрут `*` показывает `NotFoundPage`.

### Ответы

1. **Почему routes лучше локального состояния вкладки?**
   Пользователь может сохранить, отправить, перезагрузить или открыть URL в новой вкладке. Также
   правильно работают кнопки браузера Back и Forward.

2. **Что происходит при неизвестном URL?**
   React показывает страницу Not Found со ссылкой на Dashboard. Vanilla-версия при неправильном hash
   молча возвращала пользователя на Dashboard.

## Demo 9 — параметр маршрута

### Что мы изменили?

- Добавили маршрут `/team/people/:personId`.
- Каждая `PersonCard` содержит ссылку на соответствующую detail page.
- `PersonDetailsPage` читает ID и обрабатывает отсутствующие и неизвестные значения.

### Ответы

1. **Как читается и проверяется параметр?**
   `const { personId } = useParams<"personId">()` возвращает `string | undefined`. Сначала проверяем
   `undefined`, затем выполняем `people.find(...)`. Неизвестный ID показывает «Person not found», а не
   приводит к падению.

2. **Route parameter или query parameter?**
   `/team/people/nova-byte` определяет конкретного человека как основной ресурс страницы.
   `?person=nova-byte` задаёт дополнительный режим или фильтр существующей страницы. Поэтому detail
   page использует route parameter, а Timeline — query parameter.

## Demo 10 — query-параметр и завершение миграции

### Что мы изменили?

- `TimelinePage` читает `?person=...` через `useSearchParams`.
- Правильный ID фильтрует события и задаёт начальное значение select.
- Неизвестный ID показывает предупреждение, после чего выводятся все события.
- Dashboard, People & Locations и Timeline работают как React routes без ручного создания DOM.

### Ответы

1. **Почему это ещё не полноценная интерактивность?**
   Представление вычисляется напрямую из URL и props. Собственного изменяемого состояния фильтров и
   обработчиков `onChange` у select пока нет. URL только задаёт отображаемое начальное состояние.

2. **Что нужно для работающих фильтров?**
   Нужны `onChange`, controlled `value` и состояние через `useState` или `useReducer`. На основе этого
   состояния нужно вычислять видимый список. При необходимости state можно синхронизировать обратно
   в URL.

3. **Какая повторяющаяся логика пока не вынесена?**
   В `DashboardPage` есть локальная функция `formatDate`, а Timeline использует общую функцию из
   `src/shared/utils.ts`. Мы не меняли это, чтобы не расширять объём миграции. Позже Dashboard тоже
   должен использовать общую функцию.
