## Шаг 2. Сделать чистую загрузку данных для React

### Проблема старого loader

Нельзя просто импортировать `src/app/data.ts` в React. Этот файл не только загружает JSON. Он ещё:

- меняет общий объект `state`;
- вызывает старые render-функции;
- ищет элементы через `document.getElementById`;
- обновляет старый DOM.

React нужен другой loader: он только загружает и проверяет данные, а потом возвращает их.

### Что нужно понять

Хорошее разделение выглядит так:

```text
loader получает данные
  → App получает данные через props
  → компоненты описывают UI через JSX
```

Loader не должен знать, как выглядит Dashboard.

Полезные понятия:

- `Promise` — будущий результат асинхронной операции;
- `async/await` — удобный способ дождаться Promise;
- `Promise.all` — параллельно дождаться нескольких независимых запросов;
- `unknown` — данные пока неизвестной формы;
- type guard — runtime-проверка, после которой TypeScript разрешает считать значение нужным типом;
- `response.ok` — успешен ли HTTP-ответ.

### Какие файлы нужны

Рекомендуемый минимум:

```text
src/shared/data/loadInvestigationData.ts
src/shared/data/validation.ts
```

Можно добавить общий тип:

```ts
type InvestigationData = Readonly<{
  caseData: CaseData;
  people: readonly Person[];
  locations: readonly Location[];
  evidence: readonly Evidence[];
  timeline: readonly TimelineEvent[];
}>;
```

### Что я делаю

1. Выношу или создаю чистые проверки данных.
2. Загружаю пять JSON-файлов.
3. Для каждого ответа проверяю `response.ok`.
4. Считаю результат `response.json()` неизвестным до проверки.
5. Возвращаю один объект `InvestigationData`.
6. Не импортирую `src/modules/*`, старый `state` и старые render-функции.
7. Для URL использую Vite base, чтобы данные работали и на GitHub Pages.

### Как загрузить данные без лишнего React-state

В `src/react/main.tsx` можно сначала дождаться loader, а затем передать результат в `App`:

```text
loadInvestigationData()
  → <App data={data} />
```

Для ошибки загрузки нужно показать понятный React error screen. Loading также должен быть React/HTML,
а не ручным изменением старого DOM.

### Как я проверяю

- В Network вижу пять успешных JSON-запросов.
- При неправильном URL данных вижу понятную ошибку, а не пустую страницу.
- `/` по-прежнему запускает vanilla-приложение.
- `npm run typecheck` проходит.
- В loader нет `document`, `innerHTML` и вызовов UI-функций.

## Шаг 4. Перенести Dashboard в React — Demo 10

### Главная идея

Старый Dashboard строил большую HTML-строку и записывал её через `innerHTML`.

React Dashboard должен делать другое:

```text
данные
  → маленькие компоненты с props
  → JSX
  → React обновляет DOM
```

### Дерево компонентов

Начать с такого разбиения:

```text
DashboardPage
├─ CaseSummary
├─ DashboardStats
│  └─ StatCard × несколько
├─ ReviewProgress
├─ RecentEvidence
└─ RecentTimeline
```

Не нужно создавать отдельный компонент для каждого `<p>`. Компонент нужен, когда у блока есть
понятная ответственность, повторение или собственный контракт props.

### Что нужно понять про props

Props — входные данные компонента. Компонент не должен менять props.

Пример мышления:

```text
DashboardPage знает все данные Dashboard
StatCard знает только label и value
RecentEvidence знает только список последних evidence
```

Чем меньше компонент знает, тем легче его проверить и переиспользовать.

### Что такое derived values

Derived value — значение, которое можно посчитать из уже имеющихся данных и не надо хранить отдельно.

Для Dashboard это:

- количество evidence;
- количество people;
- количество locations;
- количество bookmarks;
- количество reviewed evidence;
- процент review progress;
- последние пять evidence;
- последние пять timeline events.

Такие значения надо вычислять из props, а не сохранять ещё одной копией в state.

### Что я делаю

1. Передаю данные из `App` в `DashboardPage`.
2. Создаю явно типизированные props каждого компонента.
3. Считаю reviewed status без учёта регистра.
4. При пустом evidence array возвращаю progress `0`, а не делю на ноль.
5. Для recent lists беру копию/срез массива и не мутирую входные props.
6. Отображаю пустое состояние, если recent list пуст.
7. Для list items использую стабильные `id` как `key`.
8. Не использую `innerHTML` и ручные DOM API.

### Контрольные числа текущих JSON

На чистых данных ожидаю:

```text
Evidence: 18
People: 6
Locations: 6
Reviewed: 1
Review progress: 6%
Timeline events всего: 15
```

Bookmarks зависят от `localStorage`, поэтому отдельно проверяю чистое хранилище и сохранённый
bookmark.

### Почему старый stale-data bug не должен вернуться

В старой версии существовал ручной флаг «эта страница уже отрисована». Из-за него повторный render
мог не произойти, и цифры становились устаревшими.

В React я не переношу такой флаг:

- Dashboard получает текущие props;
- при render заново вычисляет derived values;
- при возврате на Dashboard UI снова строится из тех же актуальных данных.

В vanilla эти значения пересчитывались только при явном вызове `renderDashboard()`. Ручной
render-cache мог пропустить такой вызов. В React вычисление происходит при render самого Dashboard,
поэтому отдельный флаг «уже нарисовано» не нужен.

Важно: React помогает только если данные обновляются правильно. Будущие state-обновления всё равно
должны быть immutable.

### Как проверить уход и возврат

1. Открываю Dashboard и записываю числа.
2. Перехожу на каждый placeholder.
3. Возвращаюсь через navigation.
4. Возвращаюсь через Back button.
5. Проверяю, что числа не исчезли и не удвоились.
6. Проверяю, что JSON не загружается снова при каждом route switch.
7. Перезагружаю страницу.
8. Смотрю Console и Network.
